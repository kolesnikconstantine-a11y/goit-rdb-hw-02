# Movie Recommendation — проєктування реляційної бази даних

Навчальний проєкт із проєктування схеми даних для системи рекомендацій фільмів на PostgreSQL. Основна увага приділена реляційній моделі, обмеженням цілісності, розділенню offline- та online-ознак і забезпеченню **Point-in-Time Correctness** під час підготовки даних для машинного навчання.

> **Примітка щодо даних:** у прикладах Point-in-Time Correctness використано невеликий набір синтетичних тестових записів. Це демонстраційні дані для перевірки SQL-запитів, а не фактично завантажений набір MovieLens.

## Мета проєкту

Спроєктувати реляційну схему для навчальних даних системи рекомендацій фільмів, яка:

- зберігає користувачів, фільми, оцінки та навчальні події;
- забезпечує цілісність даних за допомогою первинних і зовнішніх ключів та `CHECK`-обмежень;
- підтримує історичні версії ознак;
- дозволяє отримувати ознаки, які були доступні саме на момент прогнозу;
- розділяє історичні offline-ознаки та актуальні online-ознаки для швидкого читання.

## Структура бази даних

| `hw2_training_events` | Події для навчання моделі: користувач, фільм, момент прогнозу, горизонт мітки та цільове значення. |
| `hw2_user_features_offline` | Історичні версії ознак користувачів з інтервалами дії. |

| `hw2_user_features_online` | Поточний набір ознак користувача для швидкого online lookup. |

### Зв’язки між сутностями

- Один користувач може мати багато оцінок і навчальних подій.
- Один фільм може мати багато оцінок і навчальних подій.
- Історична таблиця ознак містить кілька версій для однієї сутності; комбінація ідентифікатора сутності та `valid_from` є первинним ключем.
- Online-таблиці містять один актуальний запис на сутність, тому `user_id` або `movie_id` є первинним ключем відповідної таблиці.

## Основні проєктні рішення

### Нормалізація та цілісність

Користувачі, фільми й оцінки зберігаються в окремих таблицях. Первинні та зовнішні ключі забезпечують унікальність записів і коректність посилань. `CHECK`-обмеження перевіряють допустимий діапазон оцінки, невід’ємність лічильників і коректність часових інтервалів.

### Offline- та online-ознаки

- **Offline-рівень** зберігає історію версій ознак із `valid_from` і `valid_to`. Це підтримує відтворюваність навчальних вибірок.
- **Online-рівень** зберігає актуальні значення ознак в одному рядку на користувача або фільм. Така денормалізація зменшує кількість операцій, потрібних для отримання ознак під час формування рекомендації.

### Індекси

Індекси на ідентифікаторах сутностей і часових мітках допомагають виконувати запити за користувачем, фільмом, часом оцінки та моментом прогнозу. Для історичних ознак передбачені індекси, що підтримують пошук версії за сутністю та `valid_from`.

## Point-in-Time Correctness

Point-in-Time Correctness означає, що для навчальної події використовуються лише ті ознаки, які були чинними на момент `prediction_ts`. Історична версія вибирається за двома умовами:

```sql
valid_from <= prediction_ts
AND (valid_to > prediction_ts OR valid_to IS NULL)
```

Інтервал **`[valid_from, valid_to)`** включає початкову мить і не включає кінцеву. Тому дві послідовні версії, одна з яких завершується в той самий момент, коли починається інша, не є одночасно чинними.

Приклад AS-OF JOIN для історичних ознак користувача:

```sql
SELECT
    e.event_id,
    e.user_id,
    e.movie_id,
    e.prediction_ts,
    e.liked,
    f.ratings_count,
    f.avg_rating
FROM hw2_training_events AS e
LEFT JOIN hw2_user_features_offline AS f
    ON f.user_id = e.user_id
   AND f.valid_from <= e.prediction_ts
   AND (f.valid_to > e.prediction_ts OR f.valid_to IS NULL)
ORDER BY e.user_id, e.prediction_ts;
```

JOIN лише за `user_id` повертає всі історичні версії користувача. Це створює дублікати навчальних подій і може додати майбутні значення ознак до минулих моментів прогнозу, спричиняючи **витік даних (data leakage)** та завищену оцінку якості моделі.

## Перевірки та результати

У ноутбуці виконано такі перевірки:

- наявність 12 історичних версій ознак для 3 тестових користувачів — по 4 версії на користувача;
- рівно одна поточна версія (`valid_to IS NULL`) для кожного тестового користувача;
- відсутність інтервалів, де `valid_to <= valid_from`;
- відсутність перекриття історичних інтервалів для тієї самої сутності;
- три AS-OF SELECT-запити, кожен із яких повернув одну відповідну версію;
- AS-OF JOIN для 9 навчальних подій, який повернув 9 рядків для 9 унікальних подій;
- відсутність подій без відповідної версії ознак;
- демонстрація некоректного JOIN за одним `user_id`, який повернув 4 версії для однієї події, включно з майбутніми значеннями.

## Reflection

Проєкт демонструє компроміс між нормалізацією та швидкістю читання. Основні сутності нормалізовані, а актуальні online-ознаки денормалізовані для швидкого доступу. Найважливішим часовим аспектом є Point-in-Time Correctness: історичні версії ознак мають приєднуватися до навчальної події відповідно до моменту прогнозу, інакше виникають дублікати та витік майбутньої інформації.

Для більшого навантаження online-рівень можна оптимізувати за допомогою попереднього обчислення ознак, індексації, кешування та горизонтального масштабування. Водночас потрібно контролювати свіжість даних. У разі еволюції схеми слід версіонувати визначення ознак, документувати зміни їхньої семантики та підтримувати сумісність зі старими версіями моделей.
